# 01 Feasibility: what a static site can really do with Garmin data, and what an iPhone home-screen web app can do

Checked 2026-11-25. Labels: **confirmed** = primary source (Garmin, Apple/WebKit, GitHub docs, or a header I observed myself); **likely** = several secondary sources agree; **unverified** = one weak source or my inference.

## What this means for us
1. **There is no way for a static website to read live Garmin data, calendar, alarms or messages.** Calendar, alarms and messages are not exposed by any Garmin API at all. So the app is honestly a **companion**: the user enters or imports things, and the app makes them fun. Never show "synced" or "live".
2. **One real import path exists: Garmin's "Export Your Data" zip**, parsed in the browser. It gives sleep, steps, stress, HRV, activities and training plans (not alarms or messages). It is a one-off file the user requests (up to 48 hours, sometimes 30 days), so it works as an occasional "refresh my stats" ritual, not a daily feed.
3. **Calendar:** import a `.ics` file (from Apple/Google Calendar, or Garmin Connect web "publish/export" which is flaky) plus manual entry. Subscribing to a live calendar URL from the browser will not work (CORS, and the URL is a secret).
4. **Alarms and messages:** manual entry only (alarm presets, quick-capture note, paste). A web app cannot ring an alarm or schedule a local notification on iPhone. Frame alarms as "mirror + check-in", never as a real alarm. A Shortcut that sends text into the app by URL does **not** work reliably (opens Safari = separate storage); use Quick add + a Paste button.
4b. **The Safari tab and the installed iPhone app do not share data.** Tell people to install first, then add data; offer export in Safari then import in the app.
5. **Hosting:** GitHub Pages on a free account needs a **public repo**. That is fine because the repo holds code and fake demo data only; every user's data stays in their own browser.

## H1: Garmin APIs (checked 2026-11-25)
- Garmin Connect Developer Program has tiers: Personal, Business Starter, Business Enterprise. Business tiers deliver data by **push to a partner's server**; Starter is push-only. Source (confirmed): https://developer.garmin.com/gc-developer-program/overview/ . Business use needs an application and there were reports the programme was paused for about 7 months and reopened 2026-10-21 (likely: https://sahha.ai/blog/garmin-connect-api-reopened-fees/ , dated 2026-11-02).
- **New: a "Personal API" exists (opened around 2026-10-21).** An individual creates a key on Garmin Connect web, exchanges it for an OAuth2 token at `https://personal.connectapi.garmin.com/personalapitoken-service/personal-api/personal-api-key/token`, token lasts 24 h, no refresh token, key lasts 30 days to 1 year. Official page (confirmed): https://developer.garmin.com/gc-developer-program/personal/personal-faq/ . It is "not intended for commercial applications serving multiple end users".
  - What it covers (likely, secondary: https://appsforstrava.com/blog/garmin-connect-developer-program-personal-api-key , updated 2026-11-06): 26 read-only endpoints for activities (JSON + FIT) and daily health (steps, stress, heart rate, sleep, HRV, Body Battery, SpO2, hydration, weight, etc.).
  - What it does **not** cover: calendar, alarms, messages, device settings. No source lists any of them (Garmin pages and 3 secondary articles are silent; the Training API that touches the calendar is business-only: https://www.tredict.com/blog/garmin_personal_api_chatgpt_and_claude/ ).
  - **Browser use is blocked (observed, my own test on 2026-11-25):** an unauthenticated CORS preflight (`OPTIONS`, `Origin: https://example.github.io`) to the token endpoint returned **HTTP 403 with no `Access-Control-Allow-Origin` header**. A browser page on github.io would not be allowed to call it. Label: **likely** (one probe, one origin; Garmin does not document CORS).
  - It would also mean pasting a long-lived secret key into the web app, which breaks our "no credentials" rule. **Decision for us: do not build on it.** Mention it in the about page as a "future idea if Garmin ever allows browser calls".
- Unofficial login-based libraries (garth, garminconnect and similar) need the user's Garmin password and are being broken by Cloudflare TLS fingerprinting (since March 2026): https://forums.garmin.com/apps-software/mobile-apps-web/f/garmin-connect-web/433892/tls-fingerprinting-blocks-third-party-clients/2022205 (likely). **We do not do that.**

## H2: Calendar
- On the watch, calendar events come from the phone's calendar via Garmin Connect mobile (permission "Calendar"); users report no way to choose which calendar (likely, forum only): https://forums.garmin.com/apps-software/mobile-apps-web/f/garmin-connect-mobile-ios/373015/how-do-i-specify-which-calendar-to-sync-with-garmin
- The Garmin Connect **web** calendar is a training/activity calendar (workouts, plans). It has a publish/export iCal feature that users report is unreliable (empty files, rolling ~30-day window, partial feeds): https://forums.garmin.com/apps-software/mobile-apps-web/f/garmin-connect-web/320386/garmin-calendar-exports-empty-vcalendar-file and https://forums.garmin.com/apps-software/mobile-apps-web/f/garmin-connect-web/60495/syncing-gc-calendar-with-external-calendar-ical-outlook-etc (likely). Importing an .ics into Garmin Connect is not supported.
- **Our route:** `.ics` file import (user exports from Apple Calendar / Google Calendar / Outlook, or Garmin web) + manual event entry + the training plan entries from the export zip. Parser must tolerate: empty files, events with no DTSTART, `VALUE=DATE` all-day events, `TZID=` and floating times, UTC `Z` times, line folding, `RRULE` (expand a limited window), UTF-8 BOM.
- Live feed URLs (webcal / Google "secret address"): not fetchable from browser JS (no CORS headers on those hosts, unverified for every host) and the URL is a secret. **Do not offer "paste your calendar URL".**

## H3: Alarms
- No Garmin API lists or sets alarms (confirmed absence in the Developer Program tiers: https://developer.garmin.com/gc-developer-program/overview/ ). Alarms are set on the watch (Garmin manual: https://www8.garmin.com/manuals/webhelp/forerunner935/EN-US/GUID-FA91A6FE-E27B-4C23-AE44-314A5B0B1F78.html ). Some models can set them in Garmin Connect mobile; users report it was removed for Forerunner 955/965 and Epix (likely): https://forums.garmin.com/developer/connect-iq/i/bug-reports/re-add-the-option-to-create-alarms-for-forerunner-955-in-garmin-connect
- Alarm counts vary by model (Venu series up to 8, per Android Authority, likely).
- **Our route:** the user types their watch's alarms (time, days, label) with quick presets; the app adds a morning "I woke up" check-in streak. Say plainly in UI copy: "This app cannot ring. Your watch does."

## H4: Messages
- iPhone: notifications you allow in iOS Settings are mirrored to the watch; the watch shows them in a notification centre (Garmin manual: https://www8.garmin.com/manuals/webhelp/GUID-C001C335-A8EC-4A41-AB0E-BAC434259F92/EN-US/GUID-5A95D297-7177-4745-ADAF-AC4855E0B7FA.html , confirmed for the mirroring). No Garmin source says a history is stored in Connect or exposed anywhere (unverified absence; I found nothing).
- **Updated 2026-11-25 (after follow-up research): a Shortcut that opens the app with the text in a URL fragment is NOT reliable. Do not ship it as a feature.**
  - A normal `https://` link in a Shortcuts "Open URL" action opens **Safari**, not the installed app (community report: https://community.glideapps.com/t/open-app-with-ios-shortcuts/21225 ; firt.dev says link capturing is unsupported on iOS: https://firt.dev/notes/pwa-ios/ , updated 2026-10-13). Safari and the installed app have **separate storage** (see H6), so the text would be saved in the wrong place and lost. Likely.
  - The `webapp://<your-start-url>` scheme does open the installed app on iOS 16.4+, but it **ignores the path** (cold start loads the start page only), so it cannot carry text: https://meta.discourse.org/t/pwa-launched-via-webapp-always-loads-homepage-not-intended-path/375036 (2025-07-21). On iOS 26 it was reported **broken** in April 2026: https://community.glideapps.com/t/ios-26-beta-opening-an-installed-web-app-with-an-open-url-action/82464 . Likely (community only; Apple documents none of it).
  - Web Share Target does not exist on iOS (below), so there is no "Share to the app" entry in the share sheet.
- **Our route:** in-app **Quick add** (big text box) and a **"Paste from clipboard" button** (`navigator.clipboard.readText()` on a tap; clipboard API supported since iOS 12 per firt.dev; iOS shows a small Paste confirmation; likely). Optional doc: "make a Shortcut that copies the text, then opens the app". If the page is opened with `#add=` in a plain Safari tab, **do not store**; show "copy this and paste it in the installed app".
- "Messages" page should be a **notes/notifications log you capture yourself**, not a mirror. Name it honestly (e.g. "Inbox" or "Pings").

## H5: Export Your Data zip
- How to get it: Garmin account data-management page, "Export Your Data", "Request Data Export", email link; typically within 48 h, up to 30 days; link expires; no date-range option (TU Delft guide https://datadonation.ide.tudelft.nl/howto/ddd_sports/ , Gadgetbridge https://gadgetbridge.org/basics/topics/garmin/import-garmin-connect/ ; likely). Garmin's own help page was not retrievable by me (403).
- Contents (community-documented, **no official schema; versions change**):
  - `DI_CONNECT/DI-Connect-Fitness/summarizedActivities.json` (one entry per activity) and raw `.fit` files, often inside nested `.zip` files (`DI-Connect-Fitness-Uploaded-Files`), split into parts for big accounts.
  - `DI_CONNECT/DI-Connect-Wellness/` sleep JSON (reported both as per-period `*_sleepData.json` and as `summarizedSleepData.json`), plus body composition etc.
  - `DI_CONNECT/DI-Connect-Aggregator/` daily summaries `UDSFile_<start>_<end>.json` (steps, resting HR, etc.).
  - `DI_CONNECT/DI-Connect-Fitness/Training/` workouts, schedules (closest thing to a calendar). Account metadata (`userProfile.json`, devices, settings) in `DI_CONNECT/DI-Connect-User/` or similar.
  - Sources: https://takeoutday.org/guides/how-to-export-garmin-connect-data (updated 2026-09-28), https://github.com/tintin305/GarminSleepAnalytics , https://forum.intervals.icu/t/which-files-are-needed-for-importing-all-garmin-data/97571 , https://forums.garmin.com/apps-software/mobile-apps-web/f/garmin-connect-web/379319/where-is-7-24-heart-rate-data (all likely/unverified on exact names).
- **Alarms and messages: not found in any description.** Device settings may exist in account metadata; unverified. Parser must be **schema-tolerant**: find files by suffix/pattern, ignore unknown ones, never crash on a missing folder.
- Size: "multi-GB for long-term athletes" (takeoutday, unverified); typical small accounts tens of MB.
- **Browser feasibility:** reading a File with `<input type="file">`, unzipping in JS (needs a zip reader: either a vendored tiny library with the lead's approval, or the browser's `DecompressionStream('deflate-raw')` plus own central-directory reader), parsing JSON. Big zips must be **streamed/sliced**, not loaded fully into an ArrayBuffer on a phone (iOS Safari memory limits; unverified numbers). Recommend: desktop is the comfortable place for the zip; on iPhone offer "pick only `summarizedActivities.json` / `*_sleepData.json` / `UDSFile*.json` files" as an escape hatch (Files app can unzip).
- Never upload; parse locally; show "nothing leaves this device" in the UI.

## H6: iPhone home-screen web app

| Capability | Verdict | Source (checked 2026-11-25) |
|---|---|---|
| Add to Home Screen opens full-screen standalone app | Yes. In iOS 26 **every** added site opens as a web app by default (user can switch off); manifest icons are used | https://webkit.org/blog/16993/news-from-wwdc25-web-technology-coming-this-fall-in-safari-26-beta/ (confirmed) |
| Web Push | Only for home-screen apps, iOS 16.4+, manifest `display: standalone`, **needs your own push server**, permission must be asked from a tap | https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/ (confirmed). **Impossible for us: no server.** |
| Local scheduled notification (no server) | **Not available.** The Notification Triggers API never shipped (Chrome origin trial ended, "launch: not started"; Safari has no `showTrigger`) | https://developer.chrome.com/docs/web-platform/notification-triggers (confirmed for Chrome status; Safari absence likely) |
| Notifications from page while open | Technically a `new Notification()` / `registration.showNotification()` needs notification permission, which iOS only grants to installed apps; it only fires while the app is running. Not useful as an alarm | WebKit post above (likely) |
| App icon badge | `navigator.setAppBadge()` works for home-screen apps, only if notification permission is granted; can be set while app is open | https://webkit.org/blog/14112/webkit-features-for-safari-17-0/ (confirmed). Optional nicety only |
| Background sync / periodic sync | Not supported on iOS (my knowledge; unverified in this session) | treat as impossible |
| Storage | IndexedDB/localStorage OK. Home-screen apps track their own "days of use", so the Safari **7-day script-storage cap is counted against actual app use** and WebKit says deletion of first-party data in them is a bug, not policy. Quotas ~15% of disk per origin for non-browser apps | https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/ and https://webkit.org/blog/14403/updates-to-storage-policy/ (confirmed). A user who opens only the **Safari tab** and does not use it for 7 days can still lose data; **tell users to install it and to export a backup now and then** |
| `navigator.storage.persist()` | WebKit grants it by heuristics (e.g. when opened as a home-screen web app); not guaranteed | https://webkit.org/blog/14403/updates-to-storage-policy/ (confirmed) |
| Web Share API (send out, incl. files) | Works since Safari 14 for text/URLs; files via `navigator.share({files})` + `canShare` (iOS 15+, my knowledge, **unverified here**: test) | https://raw.githubusercontent.com/Fyrd/caniuse/main/features-json/web-share.json (confirmed for basic support) |
| Web Share **Target** (receive from share sheet / "Open in app") | **Not supported on iOS Safari** (WebKit bug 194593 open since 2019) | https://bugs.webkit.org/show_bug.cgi?id=194593 (confirmed open status); https://tangled.org/zzstoatzz.io/plyr.fm/blob/main/docs/research/2025-12-19-web-share-target-ios-pwa.md (Dec 2025, likely) |
| Import a file | `<input type="file">` works in standalone (system picker: Files, Photos). Does NOT register the app as handler for `.ics`/`.zip`, no `file_handlers` | likely |
| Export a backup file | **Fragile.** `<a download>` with a blob has had bugs in installed iOS apps (no download, preview with no exit, app stuck after iOS 18.4). Must be tested on a real iPhone | https://bugs.webkit.org/show_bug.cgi?id=290847 , https://bugs.webkit.org/show_bug.cgi?id=275288 , https://developer.apple.com/forums/thread/95911 (likely) |
| Install steps (iOS 26) | Open the site in Safari, tap Share (three-dot menu next to the address bar, then Share), tap **Add to Home Screen**, leave **Open as Web App** switched on, optionally rename, tap **Add**. | Install prompt | No `beforeinstallprompt` on iOS: the app must show its own "Share, then Add to Home Screen" instructions | https://firt.dev/notes/pwa-ios/ (likely) |
| **Storage shared with the Safari tab?** | **No.** Installed web apps on iOS have "separate cookies and storage from the browser". Assume the installed app opens EMPTY even if you added data in a Safari tab. Install help must say "install first, then add your data" or "export in Safari, import in the app". Apple only says cookies are copied at add-time for Mac Dock apps, never local storage | https://developer.apple.com/videos/play/wwdc2023/10120/ (confirmed); https://firt.dev/notes/pwa-ios/ (likely) |
| `DecompressionStream` (unzip without a library) | Safari/iOS 16.4+ (MDN: widely available since May 2023). Known bugs: errors on big content in 16.4 (zip.js), "Extra bytes past the end" in WebKit bug 299541 (2025). | Public File System Access (`showOpenFilePicker`) | Not supported on iOS. Origin-private filesystem yes (15.2+) | https://firt.dev/notes/pwa-ios/ (likely) |
| Clipboard read | `navigator.clipboard.readText()` on a user tap, iOS 12+; shows a Paste bubble | https://firt.dev/notes/pwa-ios/ (likely) |
| Link/URL opens installed app | Not supported ("only a push message can open an installed PWA"); `webapp://` is an undocumented scheme that ignores paths and was reported broken on iOS 26 | firt.dev + Discourse + Glide links in H4 (likely) |
| Status bar / launch | `apple-mobile-web-app-status-bar-style` deprecated in iOS 15 in favour of `theme-color`; `black-translucent` is still the only way to draw under the status bar (full-bleed); startup images (`apple-touch-startup-image`) are the only splash route; `apple-touch-icon`, if present, overrides manifest icons; manifest `name` replaces `apple-mobile-web-app-title` since iOS 11.3 | https://firt.dev/notes/pwa-ios/ (likely) |

**Expectation reset for the UI:** "This is an app, not your watch. It cannot buzz your wrist, ring at 6:30 or read your messages by itself. Your watch does that. This app keeps the score and helps you plan." Put in onboarding and Settings.

## H7: GitHub Pages
- **Free plan requires a public repo** for Pages (confirmed): https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site . Pages from a **private** repo needs GitHub Pro or Team (Enterprise includes Team features): https://docs.github.com/en/get-started/learning-about-github/githubs-plans (confirmed, checked 2026-11-25). Publishing a Pages site **privately** (access-controlled) needs an organization on GitHub Enterprise Cloud, same page. So with Free/Pro/Team the published site is on the open internet even if the repo is private (inference from that page; likely). Do not put private data in the repo or the site.
- Limits (confirmed): site <= 1 GB, repo recommended <= 1 GB, 100 GB/month soft bandwidth, 10 builds/hour soft (not for Actions deploys), 10-minute deploy timeout, HTTP 429 when rate-limited. No commercial SaaS/e-commerce or sensitive data like passwords/cards. https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits
- Publish from branch + folder (`main` /root OK); Jekyll runs by default unless an empty `.nojekyll` exists (confirmed, same creating-a-site page). Project URL form `https://<user>.github.io/<repo>/` (confirmed).
- **Cache headers (observed 2026-11-25 on https://pages.github.com/):** `cache-control: max-age=600`, `access-control-allow-origin: *`, served via Fastly/Varnish. You cannot change headers on GitHub Pages (older sources, likely). Consequences: a new `sw.js` may not be seen for up to 10 minutes on browsers that obey HTTP cache for the SW script (Chrome 78+ bypasses cache for the top-level SW script; Safari behaviour unverified); **bump a `VERSION` constant in `sw.js` on every deploy**, use cache-busting `?v=` on assets or precache with revisions, and show an "update ready, tap to reload" toast. Do not cache `sw.js` from inside the SW.
- A GitHub Pages `404.html` at the site root is served for unknown paths (documented Pages behaviour; custom 404 page: https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-custom-404-page-for-your-github-pages-site , not re-fetched this session, likely). We should use **hash routing (`#/calendar`)** so no server rewrite is ever needed and the app works offline under a sub-path.
- **Observed 2026-11-25 on the public project site https://pages-themes.github.io/cayman/** (my own header checks, confirmed): `/cayman` (no trailing slash) answers **301 to `/cayman/`**; `/cayman/index.html` 200; `/cayman/INDEX.HTML` **404, so paths are case-sensitive** (lowercase every filename); a missing file returns **404 with `text/html`** (the GitHub 404 page, or the repo's `404.html` if present; no cache-control on the 404); CSS/HTML/JS get `cache-control: max-age=600` and `access-control-allow-origin: *`. Simulate exactly this in the local test server.
- Keeping data out of the public repo: the user's data is only in IndexedDB; export files are saved on the user's device; `.gitignore` `*.json` backups and `*.zip`; a privacy scan script (backend) checks for emails, phone numbers and keys before every publish.
